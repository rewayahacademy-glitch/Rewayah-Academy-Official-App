# L1-01 - Fermer `record_session_event`, `log_sensitive_access` et `materialiser_seances` aux comptes connectés

Vague 1 (sécurité). Dépend de L1-09 (stub réel), sinon le scénario de refus passe pour de mauvaises raisons.

## 1. But et pourquoi (P0-1, P1-2, P1-3, rapport section 4.1 et 4.2)

Sur STAGING, `has_function_privilege('authenticated', 'public.record_session_event(uuid,uuid,session_event_type,text)', 'EXECUTE')` vaut vrai. La fonction est SECURITY DEFINER et insère dans `session_events` sans aucune garde : n'importe quel compte connecté, un élève compris, forge une présence, un départ ou un enregistrement, ce qui commande l'absence, la paie de l'enseignant (K-45) et les corrections de la direction. Même état pour `log_sensitive_access` (une fausse ligne signée dans la chaîne d'audit) et `materialiser_seances` (création de séances pour toute affectation 1-à-1). Le seul appelant légitime de ces trois fonctions est le serveur (`service_role` : fonction Edge `livekit-webhook`, et des RPC DEFINER qui les appellent en interne).

## 2. Critère de réussite

C'est fini quand :

1. une migration horodatée retire EXECUTE à `authenticated`, `anon`, `public`, `agent_ro` sur les trois fonctions et le garde pour `service_role` ;
2. les deux fonctions INVOKER qui appellent `log_sensitive_access` (`auditer_regle_remuneration_enseignant`, `x217_valider_politique_coffres`) fonctionnent encore pour un administrateur ;
3. le scénario `supabase/tests/scenarios_af_l1_01_fonctions_serveur.sql` prouve, sous `set local role authenticated` avec un jeton administrateur, que chaque appel échoue avec `SQLSTATE 42501`, et que `has_function_privilege('service_role', ...)` reste vrai ;
4. la liste blanche de L1-09 passe après retrait des trois lignes marquées `A RETIRER PAR L1-01` ;
5. aucune ligne de `lib/` n'appelle ces trois RPC (vérifié par `grep`), donc aucun écran ne casse.

## 5. Étapes

1. Vérifier qu'aucun client n'appelle ces RPC : `grep -rn "record_session_event\|log_sensitive_access\|materialiser_seances" lib/ test/`. Résultat attendu : aucune ligne hors commentaires. Sinon, s'arrêter (section 8).
2. Lire les deux appelants INVOKER de `log_sensitive_access`. Si l'un est `security invoker`, il perdra le droit d'appeler : le redéfinir en `security definer set search_path = ''` dans la même migration, corps inchangé, en gardant sa garde positive (`if not coalesce(public.app_role() = 'admin' and public.app_account_valid(), false) then raise ...`). Si les deux sont déjà DEFINER, ne rien faire et le dire dans le commentaire d'en-tête.
3. Écrire la migration :

```sql
-- Audit final 16/10/2026, lot L1-01 (P0-1, P1-2, P1-3).
-- Ces trois fonctions n'ont qu'un appelant légitime : le serveur. Sur Supabase,
-- `authenticated` recevait EXECUTE par privilège par défaut et 0001/0005 ne le
-- retiraient pas (revoke from public ne touche pas un grant explicite).
begin;

revoke execute on function public.record_session_event(uuid, uuid, public.session_event_type, text)
  from public, anon, authenticated, agent_ro;
grant execute on function public.record_session_event(uuid, uuid, public.session_event_type, text)
  to service_role;

revoke execute on function public.log_sensitive_access(text, text, text, jsonb)
  from public, anon, authenticated, agent_ro;
grant execute on function public.log_sensitive_access(text, text, text, jsonb)
  to service_role;

revoke execute on function public.materialiser_seances(uuid)
  from public, anon, authenticated, agent_ro;
grant execute on function public.materialiser_seances(uuid)
  to service_role;

-- (étape 2 : redéfinition des appelants INVOKER, si nécessaire)

do $postflight$
begin
  if has_function_privilege('authenticated', 'public.record_session_event(uuid,uuid,session_event_type,text)', 'execute')
     or has_function_privilege('authenticated', 'public.log_sensitive_access(text,text,text,jsonb)', 'execute')
     or has_function_privilege('authenticated', 'public.materialiser_seances(uuid)', 'execute')
     or not has_function_privilege('service_role', 'public.record_session_event(uuid,uuid,session_event_type,text)', 'execute') then
    raise exception 'L1-01 postflight: privileges inattendus';
  end if;
end $postflight$;

commit;
```

   Si le rôle `agent_ro` n'existe pas dans le rejeu local (il est créé par `0014_acces_agent.sql` ou par le stub de L1-09), la migration 0014 est antérieure, donc il existe. Vérifier par `select 1 from pg_roles where rolname = 'agent_ro'`.
4. Écrire le scénario :

```sql

begin;

select set_config('request.jwt.claims', '{"app_metadata":{"role":"admin"}}', true);

do $$
begin

    perform public.record_session_event('00000000-0000-0000-0000-000000000b01', '00000000-0000-0000-0000-000000000a01', 'joined', 'test');
    raise exception 'L1-01: record_session_event accepté sous authenticated';
  exception when insufficient_privilege then null;
  end;
  begin
    perform public.log_sensitive_access('test', 'profiles', 'x', '{}'::jsonb);
    raise exception 'L1-01: log_sensitive_access accepté sous authenticated';

  end;
  begin

    raise exception 'L1-01: materialiser_seances accepté sous authenticated';

  end;
end $$;
reset role;
do $$
begin
  if not has_function_privilege('service_role', 'public.record_session_event(uuid,uuid,session_event_type,text)', 'execute') then

end $$;
```

## 7. Pièges connus

- `revoke ... from public` seul ne suffit jamais : `authenticated` a un grant explicite sur Supabase. Toujours nommer `authenticated` et `anon`.
- Le type dans la signature est `public.session_event_type` dans la migration (search_path vide) mais `session_event_type` dans le texte de `has_function_privilege`.
- `materialiser_seances` est appelée en interne par `attribuer_eleve` et `prendre_eleve` (DEFINER, propriétaires `postgres`) : le revoke ne les casse pas, parce qu'une fonction DEFINER s'exécute avec les droits de son propriétaire. Ne pas « réparer » ce qui n'est pas cassé.
- La fonction Edge `livekit-webhook` appelle `record_session_event` avec la clé de service : `service_role` doit garder EXECUTE, le postflight le vérifie.
- `exception when insufficient_privilege` attrape `42501`. Si l'erreur reçue est autre (`42883` fonction inexistante), la signature est fausse.

## 8. Quand s'arrêter et demander

- Un fichier de `lib/` ou de `supabase/functions/` appelle une des trois fonctions autrement que sous `service_role` : s'arrêter, nommer le fichier.
- Un appelant INVOKER de `log_sensitive_access` n'a pas de garde positive : ne pas inventer la garde, s'arrêter.
- Le rejeu échoue sur une migration existante : s'arrêter.
