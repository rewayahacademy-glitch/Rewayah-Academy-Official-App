# L1-04 - `mes_seances_v` : un élève ne voit que ses séances, le tuteur voit son foyer

Vague 1 (sécurité). Dépend de L1-09. Indépendant de L1-02, L1-03.

## 1. But et pourquoi (P0-2 partie fratrie, rapport section 4.1 ; doc maître 28.1 : l'enfant ne voit rien de sa fratrie)

La vue `public.mes_seances_v` (`0014_acces_agent.sql:888`) ouvre une ligne si `s.teacher_id = auth.uid()`, ou `spe.profile_id = auth.uid()`, ou `eleve.household_id = app_household_id()`, ou rôle `admin`/`controller`. La troisième clause ne regarde pas le rôle : un enfant lit les séances de ses frères et sœurs (horaires, enseignant, prénoms). Les écrans élève lisent cette vue (`lib/core/suivi/service_suivi.dart:59`, `lib/core/planning/service_planning.dart:336`).

## 2. Critère de réussite

C'est fini quand :

1. une migration horodatée redéfinit `mes_seances_v` avec une clause par rôle : `student` voit ses lignes (`spe.profile_id = auth.uid()`), `guardian` voit son foyer, `teacher` voit ses séances, `admin` tout, `controller` tout (inchangé pour lui : la vue sert au planning du contrôleur, `06` ligne Accueil par rôle), `agent_ro` ce que `0014` prévoit déjà (ne pas élargir, ne pas réduire) ;
2. le scénario `supabase/tests/scenarios_af_l1_04_mes_seances_fratrie.sql` prouve qu'un jeton `student` enfant `E` d'un foyer à deux enfants `E` et `E2` lit exactement ses séances et aucune de `E2` ; que le `guardian` lit les deux ; que l'enseignant lit les siennes ;
3. les colonnes de la vue sont strictement les mêmes qu'avant (les adaptateurs Flutter lisent par nom de colonne : `session_id`, `started_at`, `ended_at`, `status`, `session_type`, `prayer_pause_minutes`, `student_id`, `student_first_name`, `student_immutable_id`, `teacher_id`, `teacher_first_name`, `teacher_immutable_id`), vérifié par `\d+ public.mes_seances_v` avant et après ;
4. `security_barrier = true` conservé.

-- security_barrier ; seule la clause d'accès change : une clause par rôle.
begin;

create or replace view public.mes_seances_v
with (security_barrier = true)
as
select
  -- (copie exacte des colonnes de 0014:892-904)
from public.sessions s
join public.session_participants spe
  on spe.session_id = s.id and spe.role = 'student' and spe.deleted_at is null
join public.profiles eleve on eleve.id = spe.profile_id and eleve.deleted_at is null
join public.profiles ens on ens.id = s.teacher_id and ens.deleted_at is null
where s.deleted_at is null
  and public.app_account_valid()

    (public.app_role() = 'teacher' and s.teacher_id = auth.uid())

## 7. Pièges connus

- `create or replace view` refuse de changer le nom, le type ou l'ordre des colonnes existantes : si une erreur `cannot change name of view column` apparaît, c'est que la copie n'est pas exacte.
- L'adulte autonome a le rôle `student` : la clause `spe.profile_id = auth.uid()` le couvre. Ne pas ajouter de clause « foyer » pour lui.
- L'ancienne clause `s.teacher_id = auth.uid()` sans rôle servait aussi à un remplaçant ? Non : le remplaçant n'est pas `teacher_id`. Le remplaçant est traité par L2-01 (enseignant effectif) ; ne pas l'anticiper ici.
- Le contrôleur et l'administration gardent tout : c'est voulu (planning du contrôleur, exceptions de l'administration). L1-08 ajoute la validité du compte ; ici `app_account_valid()` est déjà posé en tête.
