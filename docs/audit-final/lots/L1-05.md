# L1-05 - `decider_dossier` refuse une seconde décision et un rejet retire l'accès

Vague 1 (sécurité). Dépend de L1-09. Indépendant des autres lots de la vague.

## 1. But et pourquoi (P1-1, rapport section 4.2 ; doc maître 7.3 : une décision tracée, jamais contredite en silence)

La définition STAGING de `decider_dossier(uuid, boolean, text)` (`20261012100600_f86_kyc_decision_guard.sql`) met à jour `kyc_documents.status` sans vérifier que le dossier est encore `pending`. Deux administrateurs peuvent décider dans les deux sens sans le voir ; un dossier approuvé puis rejeté garde un compte `active`, parce que le passage à `active` n'est fait que dans le sens de l'approbation (`WHERE account_status = 'pending_kyc'`), et rien n'est fait dans l'autre sens.

## 2. Critère de réussite

C'est fini quand :

1. une migration horodatée redéfinit `decider_dossier` avec, avant toute écriture, `if v_doc.status <> 'pending' then raise exception 'dossier déjà décidé' using errcode = 'check_violation'` ;
2. au rejet, si le profil est un enseignant (`teacher_profiles` existe pour lui) et que son compte est `active` ou `provisional_active` sans autre pièce `approved`, `account_status` passe à `disabled` et la raison est journalisée dans le même `log_sensitive_access('kyc_decision', ...)` par un champ `acces_retire = true` ;
3. le scénario `supabase/tests/scenarios_af_l1_05_decider_dossier_une_fois.sql` prouve : approbation puis seconde décision refusée (SQLSTATE `23514`), rejet d'un enseignant actif sans autre pièce approuvée passe `disabled`, rejet d'un enseignant qui garde une autre pièce `approved` ne touche pas `account_status` ;
4. le commentaire `md5_functiondef=` de la fonction (allowlist F86) est recalculé et les scénarios qui le vérifient passent (`scenarios_f86_admin_mutators.sql`) ;
5. l'écran d'administration (`lib/features/admin_dossiers/`) affiche l'erreur « dossier déjà décidé » comme une erreur avec action (recharger la file) : vérifier par lecture que `service_validation.dart` propage la `PostgrestException` et que `detail_dossier.dart` a un état d'erreur ; si l'erreur est avalée, le noter en section 8 pour la vague 2 (pas de modification de `lib/` dans ce lot).

## 5. Étapes

1. Copier intégralement la fonction de `20261012100600` dans la nouvelle migration. Après la ligne `IF v_doc.id IS NULL THEN ... END IF;`, insérer :

```sql
  IF v_doc.status <> 'pending' THEN
    RAISE EXCEPTION 'dossier déjà décidé' USING ERRCODE = 'check_violation';
  END IF;
```

2. Remplacer le bloc `IF p_approuve THEN UPDATE public.profiles ... END IF;` par :

```sql
  v_acces_retire := false;
  IF p_approuve THEN
    UPDATE public.profiles
    SET account_status = 'active', updated_at = now()
    WHERE id = v_doc.profile_id AND account_status = 'pending_kyc';
  ELSIF EXISTS (SELECT 1 FROM public.teacher_profiles tp WHERE tp.profile_id = v_doc.profile_id)
    AND NOT EXISTS (
      SELECT 1 FROM public.kyc_documents k
       WHERE k.profile_id = v_doc.profile_id AND k.id <> p_document_id AND k.status = 'approved'
    ) THEN
    UPDATE public.profiles
    SET account_status = 'disabled', updated_at = now()
    WHERE id = v_doc.profile_id AND account_status IN ('active', 'provisional_active');
    GET DIAGNOSTICS v_n = ROW_COUNT;
    v_acces_retire := v_n > 0;
  END IF;
```

   Déclarer `v_acces_retire boolean; v_n integer;` dans le `DECLARE`. Vérifier dans `0001_fondations.sql` que `'disabled'` est bien une valeur de l'énumération d'état de compte (chercher `account_status`) ; sinon utiliser la valeur qui signifie « suspendu » et le dire dans le commentaire.
3. Dans l'appel `log_sensitive_access`, ajouter `'acces_retire', v_acces_retire` au `jsonb_build_object`.
4. Reprendre l'ACL et le `COMMENT ON FUNCTION` de la migration d'origine. Recalculer le md5 : après rejeu local, `select md5(pg_get_functiondef('public.decider_dossier(uuid,boolean,text)'::regprocedure));` et reporter la valeur dans le commentaire, puis rejouer une seconde fois pour que le scénario F86 le lise. Reprendre aussi le `DO $postflight$` de l'origine et y ajouter `AND pg_catalog.strpos(p.prosrc, 'dossier déjà décidé') > 0`.
5. Écrire le scénario. Préparer sous `postgres` : un administrateur `A` (`role = 'admin'`, `gender` renseigné, compte actif), un enseignant `T1` avec un dossier `pending` et compte `active`, un enseignant `T2` avec un dossier `pending` et un autre dossier `approved`, compte `active`. Lire `scenarios_c21_kyc_access_verdict.sql` pour la forme des lignes `kyc_documents` et pour le cloisonnement de genre (`read_kyc_documents` filtre par genre : l'administrateur et les enseignants du test doivent avoir le genre qui permet la lecture, ou `A` doit être super-administrateur selon `0088`). Puis, sous jeton `A` :

```sql
do $$ begin
  perform public.decider_dossier('<doc T1>', true, null);
  begin
    perform public.decider_dossier('<doc T1>', false, 'test');
    raise exception 'L1-05: seconde décision acceptée';
  exception when check_violation then null;
  end;
end $$;
```

   Vérifier ensuite sous `postgres` : `T1.account_status = 'active'` (l'approbation tient). Rejeter le dossier `pending` de `T2` : `T2.account_status` inchangé (autre pièce approuvée). Préparer un `T3` enseignant actif avec une seule pièce `pending`, la rejeter : `T3.account_status = 'disabled'`, et la dernière ligne de `audit_logs` pour `kyc_decision` porte `payload ->> 'acces_retire' = 'true'`.
6. Rejouer tout sur PostgreSQL 17 neuf : migrations, 15 scénarios CI, `scenarios_f86_admin_mutators.sql`, `scenarios_c21_kyc_access_verdict.sql`, nouveau scénario. Le nouveau doit échouer sans la migration (« seconde décision acceptée »).

## 7. Pièges connus

- Le md5 change à chaque caractère : calculer après le dernier rejeu, puis rejouer encore une fois pour prouver que le scénario F86 passe avec la valeur inscrite.
- `read_kyc_documents()` filtre par genre du lecteur (`0088`) : un dossier « introuvable ou hors du périmètre » dans le scénario vient presque toujours d'un genre manquant sur l'administrateur ou l'enseignant de test, pas de la fonction.
- Ne pas désactiver un tuteur au rejet : K-47 ne lui demande aucune pièce, et son compte ne dépend pas du KYC. La condition `teacher_profiles` l'exclut.
- `account_status` est protégé par le trigger `guard_profile_privileged_columns` (0084) : la fonction est DEFINER propriétaire `postgres`, donc `current_user = 'postgres'` passe la garde. Si le rejeu dit `seul un admin modifie rôle, foyer, statut ou accès`, c'est que `current_user` n'est pas `postgres` : lire la garde avant de toucher quoi que ce soit.

## 8. Quand s'arrêter et demander

- La valeur `disabled` n'existe pas dans l'énumération : s'arrêter, lister les valeurs.
- Un enseignant peut légitimement avoir deux pièces (recto et verso, ou pièce et justificatif) : si la table distingue des types de pièce (`kind`, `doc_type`), s'arrêter et demander si « aucune autre pièce approuvée » doit se lire par type.
- L'écran d'administration avale l'erreur (étape 5 du critère) : ne pas corriger `lib/`, le signaler.
