# L1-06 - Le grand livre `wallet_entries` ne se modifie ni ne s'efface

Vague 1 (sécurité). Dépend de L1-09. Indépendant des autres lots.

## 1. But et pourquoi (P1-4, rapport section 4.2 ; doc maître 13.2 : les écritures financières sont un journal, les corrections sont des écritures inverses)

Sur STAGING, `wallet_entries_admin_accountant_all` est `FOR ALL` et `authenticated` a UPDATE et DELETE sur la table. Un administrateur ou un comptable réécrit ou efface un montant encaissé par REST, sans trace : le seul trigger est `x217_guard_confirmation_source`. Le journal d'audit (`audit_logs`) a déjà le bon modèle : `guard_audit_logs_immutable` (`0001_fondations.sql:567-582`) refuse UPDATE et DELETE.

## 2. Critère de réussite

C'est fini quand :

1. une migration horodatée crée `guard_wallet_entries_immutable()` sur le modèle de `guard_audit_logs_immutable()`, attachée `before update or delete on public.wallet_entries`, qui lève `insufficient_privilege` pour tout rôle, `postgres` et `service_role` compris, sauf un chemin explicite de suppression logique s'il en existe un (il n'en existe pas : la table n'a pas de `deleted_at`) ;
2. la même migration remplace `wallet_entries_admin_accountant_all` (FOR ALL) par deux policies `wallet_entries_admin_accountant_read` (SELECT) et `wallet_entries_admin_accountant_insert` (INSERT), toutes deux avec `coalesce(app_role() in ('admin','accountant') and app_account_valid(), false)` ;
3. `revoke update, delete on public.wallet_entries from authenticated, anon, agent_ro` ;
4. le scénario `supabase/tests/scenarios_af_l1_06_ledger_immuable.sql` prouve : un `admin` insère une écriture ; son `update` et son `delete` échouent (42501 ou zéro ligne) ; même sous `postgres`, `update` lève `insufficient_privilege` ; une écriture inverse (`reference_type = 'adjustment'`, montant négatif) s'insère ;
5. les RPC qui écrivent dans `wallet_entries` (chercher `insert into public.wallet_entries` dans les migrations) n'en font jamais d'`update` ni de `delete` ; si l'une le fait, voir section 8.

## 5. Étapes

1. Vérifier l'absence d'`update`/`delete` serveur et client sur la table (section 3). Résultat attendu : aucun. Sinon section 8.
2. Écrire la migration :

```sql
-- Audit final 16/10/2026, lot L1-06 (P1-4). Le grand livre est un journal :
-- on n'y corrige qu'en écrivant l'inverse. Même modèle que audit_logs (0001).
begin;

create or replace function public.guard_wallet_entries_immutable()
returns trigger
language plpgsql
security definer
set search_path = ''
as $$
begin
  raise exception 'wallet_entries est immuable : écrire une écriture inverse (adjustment)'
    using errcode = 'insufficient_privilege';
end;
$$;
revoke all on function public.guard_wallet_entries_immutable() from public, anon, authenticated, agent_ro;

drop trigger if exists wallet_entries_no_update on public.wallet_entries;
create trigger wallet_entries_no_update
  before update on public.wallet_entries
  for each row execute function public.guard_wallet_entries_immutable();

drop trigger if exists wallet_entries_no_delete on public.wallet_entries;
create trigger wallet_entries_no_delete
  before delete on public.wallet_entries
  for each row execute function public.guard_wallet_entries_immutable();

drop policy if exists wallet_entries_admin_accountant_all on public.wallet_entries;
create policy wallet_entries_admin_accountant_read on public.wallet_entries
  for select to authenticated
  using (coalesce(public.app_role() in ('admin', 'accountant') and public.app_account_valid(), false));
create policy wallet_entries_admin_accountant_insert on public.wallet_entries
  for insert to authenticated
  with check (coalesce(public.app_role() in ('admin', 'accountant') and public.app_account_valid(), false));

revoke update, delete on public.wallet_entries from authenticated, anon, agent_ro;

do $postflight$
begin
  if exists (select 1 from pg_policies where tablename = 'wallet_entries' and policyname = 'wallet_entries_admin_accountant_all') then
    raise exception 'L1-06 postflight: policy FOR ALL encore présente';
  end if;
  if has_table_privilege('authenticated', 'public.wallet_entries', 'update')
     or has_table_privilege('authenticated', 'public.wallet_entries', 'delete') then
    raise exception 'L1-06 postflight: authenticated garde update ou delete';
  end if;
end $postflight$;

commit;
```

   Vérifier que la policy d'origine était déclarée `to authenticated` ou `to agent_ro, authenticated` (MESURES 3.3 dit `{agent_ro, authenticated}`) : reprendre la même liste de rôles pour la lecture ; pour l'insertion, `authenticated` seul.
3. Écrire le scénario : sous `postgres`, un foyer et un `wallets` ; sous jeton `admin` valide, `insert into public.wallet_entries (wallet_id, amount_minor, currency, reference_type) values (..., 1000, 'EUR', 'credit')` réussit ; `update ... set amount_minor = 1` : attraper `insufficient_privilege` ; `delete` : idem ; insérer `(-1000, 'adjustment')` : réussit ; sous `postgres`, `update` doit aussi lever `insufficient_privilege`. Sous jeton `admin` suspendu (`account_status = 'disabled'`), `select count(*)` vaut 0.
4. Rejouer tout sur PostgreSQL 17 neuf. Le scénario doit échouer sans la migration (l'update passe).

## 7. Pièges connus

- `drop policy` puis `create policy` est obligatoire ici : `alter policy` ne change pas `FOR ALL` en `FOR SELECT`.
- Le trigger refuse aussi `postgres` : c'est voulu (modèle `audit_logs`). Une migration future qui devrait corriger une ligne devra désactiver le trigger explicitement dans la migration, et le dire.
- La policy `wallet_entries_family_read` est traitée par L1-02 : ne pas la toucher ici (conflit de fichiers évité parce que chaque lot a sa migration ; conflit de sens évité parce que les deux `alter`/`create` portent des noms différents).
- `reference_type` est contraint à `('credit', 'debit', 'adjustment', 'payout')` : l'écriture inverse est un `adjustment`.

## 8. Quand s'arrêter et demander

- Une RPC existante fait `update` ou `delete` sur `wallet_entries` : s'arrêter, la nommer ; la bonne correction est dans cette RPC, pas dans le trigger.
- Un scénario existant nettoie la table par `delete` : s'arrêter, le nommer.
