# L1-08 - Les 45 policies par rôle vérifient aussi que le compte est valide

Vague 1 (sécurité). Dépend de L1-09. À lancer après L1-06 (qui remplace `wallet_entries_admin_accountant_all`) pour éviter un `alter policy` sur une policy disparue ; indépendant des autres.

## 1. But et pourquoi (P1-6 et P2-1 journal, rapport section 4.2 ; doc maître 28.3 : un compte suspendu perd ses droits immédiatement, pas à l'expiration du jeton)

Cinquante policies de `public` testent `app_role()` sans `app_account_valid()` (liste complète : `docs/audit-final/MESURES-2026-10-16.md` section 3.2). Un administrateur, un comptable ou un contrôleur suspendu (`account_status = 'disabled'`) garde ses droits REST pendant la vie de son jeton, soit une heure : `profiles_admin_all`, `sessions_admin_all`, `audit_logs_read`, `verset_admin`, etc. Les RPC, elles, sont déjà gardées (`coalesce(app_role() = 'admin' and app_account_valid(), false)`, F86). Ce lot aligne les policies sur les RPC. Il réduit aussi `audit_logs_read` au seul administrateur (le contrôleur lisait tout le journal, payloads KYC et jetons vidéo compris : P2-1).

## 2. Critère de réussite

C'est fini quand :

1. une migration horodatée fait un `alter policy ... using (...) [with check (...)]` sur 45 des 50 policies de la liste (toutes sauf les cinq de lecture pour rôles non privilégiés : `offres_horaires_vitrine`, `profiles_family_select`, `households_guardian_select`, `srp_foyer_lecture`, `intentions_horaire_parties`, laissées au relecteur, et sauf `wallet_entries_admin_accountant_all` déjà remplacée par L1-06), en enveloppant l'expression existante : `coalesce((<expression actuelle>) and public.app_account_valid(), false)` ;
2. `audit_logs_read` devient `coalesce(public.app_role() = 'admin' and public.app_account_valid(), false)` ;
3. le scénario `supabase/tests/scenarios_af_l1_08_compte_suspendu.sql` prouve, pour un jeton `admin` dont le profil est `account_status = 'disabled'`, zéro ligne lue sur `profiles`, `sessions`, `audit_logs`, `app_config`, `wallets`, et zéro ligne écrite (`update profiles set first_name` sur un autre profil : `row_count = 0`) ; pour un jeton `controller` valide, zéro ligne sur `audit_logs` ; pour un `admin` valide, les lignes attendues ;
4. un contrôle automatique dans le même scénario compte les policies de `public` dont `qual || with_check` contient `app_role()` sans `app_account_valid` et exige que le compte soit égal à 5 (les cinq laissées), avec leur liste en message si ce n'est pas le cas.

## 5. Étapes

Exporter les 50 policies : `psql -At -c "select policyname || E'\t' || cmd || E'\t' || coalesce(qual,'') || E'\t' || coalesce(with_check,'') from pg_policies where schemaname='public' and policyname in (<les 50 noms>)" > /tmp/policies.tsv`.
2. Générer la migration à partir de cet export, une instruction par policy, sans rien taper à la main :
   - si `cmd` est `SELECT` ou `DELETE` : `alter policy <nom> on public.<table> using (coalesce((<qual>) and public.app_account_valid(), false));`
   - si `cmd` est `INSERT` : `alter policy <nom> on public.<table> with check (coalesce((<with_check>) and public.app_account_valid(), false));`
   - si `cmd` est `UPDATE` ou `ALL` : les deux clauses, chacune enveloppée ; si `with_check` est vide pour un `ALL`, PostgreSQL applique `qual` aux écritures : n'ajouter `with check` que s'il existait.
   - Exception `audit_logs_read` : remplacer entièrement par `using (coalesce(public.app_role() = 'admin' and public.app_account_valid(), false))`.
   - Sauter les cinq policies laissées et `wallet_entries_admin_accountant_all`.
   Les expressions exportées écrivent `app_role()` sans préfixe : les préfixer `public.` dans la migration (search_path vide dans les scénarios, pas dans les policies, mais la cohérence évite une erreur de rejeu).
3. Ajouter en tête de la migration un commentaire qui liste les 44 policies modifiées et les 6 laissées, avec la raison.
4. Postflight dans la migration :

```sql
do $postflight$
declare v_liste text;
begin
  select string_agg(tablename || '.' || policyname, ', ' order by 1) into v_liste
    from pg_policies
   where schemaname = 'public'
     and (coalesce(qual,'') || coalesce(with_check,'')) like '%app_role()%'
     and (coalesce(qual,'') || coalesce(with_check,'')) not like '%app_account_valid%';
  if v_liste is distinct from 'households.households_guardian_select, intentions_horaire.intentions_horaire_parties, offres_horaires.offres_horaires_vitrine, profiles.profiles_family_select, student_reading_position.srp_foyer_lecture' then
    raise exception 'L1-08 postflight: policies sans app_account_valid : %', coalesce(v_liste, '(aucune)');
  end if;
end $postflight$;
```

## 7. Pièges connus

- `alter policy` échoue si la policy n'existe plus (`wallet_entries_admin_accountant_all` après L1-06) ou si son nom a changé : d'où l'export depuis la base rejouée, pas depuis les migrations.
- `coalesce(x and y, false)` : si `app_role()` rend NULL (jeton sans rôle), `x` est NULL, `x and y` est NULL ou faux, `coalesce` donne faux. C'est la forme F86 ; ne pas écrire `x and y` nu.
- `app_account_valid()` est `stable`, DEFINER, exécutable par `anon` et `authenticated` : la policy peut l'appeler. Coût : une lecture de `profiles` par requête, déjà payée par les RPC.
- `profiles_admin_all` : l'administrateur suspendu ne lit plus sa propre ligne ; `profiles_self_select` (si elle existe) la lui rend. Si l'écran « compte suspendu » a besoin de lire son profil pour l'afficher, vérifier qu'une policy `self` existe sans rôle.
- `kyc_guardian_insert` est dans la liste : P3-2 propose de la supprimer (le tuteur ne dépose plus de pièce). Ici, seulement l'envelopper ; la suppression est une décision déjà prise (K-47) mais hors de ce lot.
