# L1-09 - Le stub de CI reproduit les privilèges de Supabase, et une liste blanche des fonctions volatiles

Vague 1 (sécurité). Premier lot de la vague : les lots L1-01 à L1-08 ont besoin de ce stub pour que leurs scénarios de refus veuillent dire quelque chose.

## 1. But et pourquoi (P1-7, rapport section 4.2)

Sur un projet Supabase, le rôle `authenticated` reçoit EXECUTE sur toute fonction créée dans `public` par privilège par défaut, et `anon` aussi. Le stub `supabase/tests/stub_auth.sql` crée les rôles sans ces privilèges par défaut. Résultat : une fonction que le dépôt croit fermée (`record_session_event`, fermée par `0001_fondations.sql:1209-1214` avec `revoke ... from anon, public`) est en réalité exécutable par tout compte connecté sur STAGING (P0-1), et la CI ne le voit pas. Ce lot rend la CI honnête, puis fige par une liste blanche l'ensemble des fonctions volatiles qu'un compte connecté a le droit d'appeler. Il prépare aussi, dans `docs/`, le texte exact des modifications de `.github/workflows/ci.yml` que seul le directeur peut poser (arbitrage A-10).

## 2. Critère de réussite

C'est fini quand :

1. le stub pose les mêmes privilèges par défaut que Supabase pour `anon`, `authenticated`, `service_role` sur le schéma `public` (fonctions, tables, séquences) ;
2. les 199 migrations se rejouent toujours sans erreur sur un PostgreSQL 17 neuf avec ce stub ;
3. les 15 scénarios de la CI passent toujours dans l'ordre de `ci.yml` ;
4. un nouveau scénario `supabase/tests/scenarios_af_liste_blanche_volatiles.sql` échoue si une fonction volatile du schéma `public` est exécutable par `authenticated` sans figurer dans sa liste, ou par `anon` tout court ;
5. ce scénario échoue avant L1-01 (il doit nommer `record_session_event`, `log_sensitive_access`, `materialiser_seances` dans sa liste avec la mention `-- A RETIRER PAR L1-01`) et le relecteur de L1-V vérifie qu'il passe après L1-01 sans ces trois lignes ;
6. `docs/audit-final/ci/ci.yml.propose.md` contient les blocs YAML prêts à coller pour : rejouer les 74 scénarios, faire tourner le job Flutter sur les PR vers `ccr-1b1bfa0b-m1kvkk` et `claude/backend-reprise`, ajouter `needs` dans `deploy.yml`, liste blanche des deux empreintes de test de la garde anti-secret.

6. Produire la liste des fonctions volatiles exécutables par `authenticated` sur `apres` :

7. Écrire `supabase/tests/scenarios_af_liste_blanche_volatiles.sql` :

```sql
-- Liste blanche des fonctions volatiles de `public` exécutables par un compte
-- connecté. Audit final 16/10/2026, lot L1-09. Toute fonction qui apparaît
-- ici a été relue : garde positive sur le rôle ET app_account_valid(), ou
-- fonction d'écriture volontairement ouverte. Ajouter une ligne = une relecture.
begin;
do $$
declare
  v_liste text[] := array[
    'public.accepter_demande_presentation(uuid)',
    -- ... une ligne par fonction de l'étape 6, triée, avec sa signature
    'public.record_session_event(uuid,uuid,session_event_type,text)',  -- A RETIRER PAR L1-01
    'public.log_sensitive_access(text,text,text,jsonb)',               -- A RETIRER PAR L1-01
    'public.materialiser_seances(uuid)'                                -- A RETIRER PAR L1-01
  ];
  v_hors_liste text;
  v_anon text;
begin
  select string_agg(p.oid::regprocedure::text, ', ' order by 1) into v_hors_liste
    from pg_proc p join pg_namespace n on n.oid = p.pronamespace
   where n.nspname = 'public' and p.prokind = 'f' and p.provolatile = 'v'
     and has_function_privilege('authenticated', p.oid, 'execute')
     and not (p.oid::regprocedure::text = any (v_liste));
  if v_hors_liste is not null then
    raise exception 'AF-LB: fonctions volatiles exécutables par authenticated hors liste blanche : %', v_hors_liste;
  end if;
  select string_agg(p.oid::regprocedure::text, ', ' order by 1) into v_anon
    from pg_proc p join pg_namespace n on n.oid = p.pronamespace
   where n.nspname = 'public' and p.prokind = 'f' and p.provolatile = 'v'
     and has_function_privilege('anon', p.oid, 'execute')
     and not exists (select 1 from pg_depend d where d.objid = p.oid and d.deptype = 'e');
  if v_anon is not null then
    raise exception 'AF-LB: fonctions volatiles exécutables par anon : %', v_anon;
  end if;
end $$;
rollback;
```

   Les fonctions d'extension (`btree_gist`, exclues par `pg_depend deptype = 'e'`) ne comptent pas pour `anon` : c'est P3-1, hors de ce lot.

## 7. Pièges connus

- Une migration qui échoue sous le nouveau stub mais passait avant : ne pas l'éditer. Comparer la fonction visée avec STAGING (`MESURES` section 3.1). Si STAGING a le même privilège que le rejeu local, le postflight de la migration est faux et c'est un vrai défaut : s'arrêter et le signaler (section 8). Si STAGING n'a pas le privilège, chercher quelle migration ultérieure le retire et laisser passer.
- `alter default privileges for role postgres` ne vaut que pour les objets créés par `postgres`. La CI lance `psql -U postgres` : c'est le cas. En local, utiliser aussi `-U postgres`.
- `has_function_privilege` lève une erreur si la signature n'existe pas : écrire la liste blanche avec `p.oid::regprocedure::text`, jamais avec des signatures tapées à la main.
- Le texte de `regprocedure` écrit `session_event_type` sans préfixe `public.` dans la signature, et les types `smallint` deviennent `smallint`, `integer` reste `integer`. Copier la sortie de l'étape 6 telle quelle.
- Le scénario `b18_security_definer.sql:5` fait `REVOKE SELECT ON public.kyc_documents FROM authenticated` : avec les nouveaux privilèges par défaut, ce revoke devient effectif (avant, il ne retirait rien). Si `b18` échoue plus loin, lire pourquoi avant de conclure.
