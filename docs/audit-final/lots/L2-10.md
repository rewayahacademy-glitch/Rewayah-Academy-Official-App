# L2-10 - Une annonce de l'académie apparaît une fois chez un tuteur à deux Classes ; le test rouge des annonces redevient vert

Vague 2 (raccordements). Dépend de L1-V. Indépendant des autres lots.

## 1. But et pourquoi (matrice R-02, T-14 ; `AUDIT-ETAT-2026-10-16.md` ; `20261016102300_raccordement_annonces_academie.sql`)

`com_annonces_academie(p_groupe_id)` rend les annonces générales « dans le contexte de cette Classe » ; `com_annonces_de_classe` ne rend que celles de la Classe ; « l'adaptateur client fusionne les deux lectures » (commentaire de la migration). Un tuteur dont le foyer a deux Classes voit l'annonce de l'académie deux fois (une par Classe), constaté dans `AUDIT-ETAT-2026-10-16.md`. De plus, `test/features/com_annonces/demo_annonces_test.dart`, test « La démonstration rendue famille, 390 : R-COM-12 de bout en bout, la lecture suit », est rouge sur le commit audité (`MESURES` section 5.3) : seul test rouge de la base.

## 2. Critère de réussite

C'est fini quand :

1. l'adaptateur client des annonces (`lib/core/communications/*annonces*_supabase.dart`, à localiser : `grep -rln "com_annonces_academie\|com_annonces_de_classe" lib/core`) dédoublonne par `id` d'annonce après la fusion, en gardant la première occurrence (la Classe la plus récente ou la première listée), et le port rend une liste sans doublon ;
2. si l'adaptateur appelle `com_annonces_academie` une fois par Classe, il l'appelle une seule fois avec `p_groupe_id = null` (ou la première Classe) et fusionne ensuite avec les annonces de chaque Classe ; la lecture d'une annonce générale (`com_annonce_lire`, `com_annonce_marquer_lue`) continue de fonctionner (elle ne dépend pas de la Classe de contexte) ;
3. un test `test/core/communications/annonces_dedoublonnage_test.dart` prouve avec le faux client : deux Classes, une annonce générale `A` et une annonce de Classe par Classe : la liste rendue contient `A` une fois et les deux annonces de Classe ;
4. le test rouge « famille, 390 : R-COM-12 de bout en bout, la lecture suit » est vert : lire d'abord l'exception exacte (`flutter test test/features/com_annonces/demo_annonces_test.dart --plain-name "R-COM-12"`), la corriger à la racine (dans la démonstration ou dans l'écran), jamais en modifiant l'assertion sans comprendre ; si la cause est le doublon (deux annonces identiques trouvées là où le test en attend une), le point 1 le corrige ;
5. `flutter test test/features/com_annonces` vert en entier.

## 7. Pièges connus

- Une annonce générale « dans le contexte d'une Classe » porte `classe` non nul : après dédoublonnage, le libellé de Classe affiché sur l'annonce générale peut être celui d'une Classe arbitraire. Préférer afficher la portée (« Toute l'académie » / « كل الأكاديمية », clé existante à chercher dans `com.*`) plutôt que la Classe pour les annonces à `portee` différente de Classe. Si cela demande une clé i18n nouvelle, FR et AR avec source.
- `lue` est par profil : deux occurrences ont la même valeur `lue` ; la dédoublonnage ne perd rien.
- Le test rouge peut venir d'un `pumpAndSettle` qui n'attend pas la latence de démonstration : lire avant de conclure au doublon.

## 8. Quand s'arrêter et demander

- La cause du test rouge est un changement de contrat serveur (clé jsonb renommée) : s'arrêter, nommer la clé ; la correction est côté adaptateur mais le contrat (onglet Contrats) doit être relu.
- Le dédoublonnage ne peut pas se faire au client sans perdre le marquage « lue » par Classe : s'arrêter.
