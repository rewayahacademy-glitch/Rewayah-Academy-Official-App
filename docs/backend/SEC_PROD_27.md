# SEC-PROD : les 27 fonctions SECURITY DEFINER exposees a anon (DEFINER ou INVOKER ?)

Source des 27 signatures : le bloc `revoke all on function ... from public, anon` de `SEC_PROD_REMEDIATION.sql` (branche `codex/backend-sec-prod-m2-fixes` @ 466bc63c, lignes 769-795), qui correspond au controle « exposition anon SECURITY DEFINER = 27 » du preflight. Analyse sur le catalogue ACTIF de `codex/backend-canon-fixes` @ ea1a0da9 (Postgres 16.15, stub_auth + 102 migrations).

Cles de lecture. **RLS** : la fonction lit ou ecrit une table a RLS. **get_config / regle_brute** : appelle une fonction interne dont l'ACL n'accorde pas `authenticated` (`get_config(text,jsonb)` et `regle_brute(uuid,text)` : postgres + service_role seulement). **auth** : appelle `auth.uid()`/`auth.jwt()`. **storage** : aucune des 27 ne touche `storage.*`. Une conversion en INVOKER fait tourner la fonction avec les droits de l'appelant : elle ne marche que si l'appelant a le droit de lecture/ecriture sur les tables touchees ET le droit d'executer les fonctions appelees.

Constat sur le catalogue actif : `guard_profile_privileged_columns()` est deja **INVOKER** (prosecdef = false). `rls_auto_enable()` est **absente** du schema `public` de canon-fixes (fonction plateforme Supabase, evenement DDL ; elle n'existe que sur PROD). L'ACL de la table ci-dessous est celle de canon (certaines fonctions y portent encore `anon`, que le script retire), pas celle de PROD.

Regle de prudence : tant que la fonction est appelee par une policy RLS ou un trigger, la convertir en INVOKER change le role d'execution dans toutes les politiques qui l'appellent : a ne faire que sur les triggers purs (aucune lecture), pas sur les helpers de policy.

## Notes pour Codex

1. **Declencheurs INVOKER.** Les six triggers marques INVOKER ne lisent rien : les convertir (`alter function ... security invoker`) est sans effet fonctionnel et retire six fonctions de la liste des DEFINER a surveiller. Le test d'acceptation est `supabase/tests` existant : rejouer les scenarios du depot apres conversion. Les `revoke ... from public, anon` du script restent utiles pour les deux autres ACL (aucun trigger ne requiert `EXECUTE` au declenchement).
2. **Helpers de policy (`app_*`, `profil_de_mon_foyer`, `agent_identite_masquee`).** Ne pas les convertir : ils sont appeles dans les policies de presque toute la base, y compris celles de `profiles` (recursion) et celles d'agent_ro, qui n'a pas `USAGE` sur le schema `auth` dans le catalogue canon.
3. **`agent_pre_request()`** doit conserver `grant execute ... to anon` (appel PostgREST avant authentification), comme le script le fait deja.
4. **`rls_auto_enable()`** n'existe pas sur canon : le preflight « 27 » du script suppose le catalogue PROD ; sur un Postgres nu rejoue depuis les migrations on obtient 26 signatures et le preflight devrait etre recalibre pour toute execution hors PROD.
5. Aucune des 27 ne lit `storage.*` ni n'ecrit `auth.*`. Seules `agent_pre_request` (set_config) et les helpers JWT touchent la couche auth.
